## The Rule: One Source of Truth Per File Type

Every file type has exactly one home. Duplication is a smell — if something exists in two places, one copy should be a link/reference to the other.

## Decision Rules

**"Is this a decision or governance doc?"**  
→ GitHub (public) — `smoking-tigers-governance` repo

**"Is this a team reference document (how-to, SOP, member guide)?"**  
→ Notion (member-facing) OR GitHub (if it should be forkable/public)

**"Is this raw media or a big binary file?"**  
→ Google Drive (shared)

**"Was this generated by an agent in a session?"**  
→ OpenProject — attach to the relevant work package

**"Is this a daily working note or in-progress scratch?"**  
→ Local `~/Discovery/` — it's working memory, not canonical

**"Should other STE members or AI agents be able to access this?"**  
→ If yes: OP database, Notion, or Google Drive. NOT local.

## Git + GitHub Specifics

- **Public repos** (`smoking-tigers-governance`, `smokingtigers.enterprises`): governance docs, website, open-source specs — things you want people to fork and build on
- **Private repos**: proprietary configs, internal agent specs, things not yet ready to be public
- GitHub is **not** for raw notes, personal working memory, or large binary files

## Issue Tracking

**"I found a bug or issue — where does it go?"**

→ GitHub Issues on the relevant repo. Steps:
1. Go to the repo on GitHub
2. Click **Issues** → **New issue**
3. Title: short description
4. Body: steps to reproduce + expected vs actual behavior
5. Label: `bug`, `question`, or `enhancement`

Your agent can do this with your GitHub PAT. Ask it: *"Create a GitHub issue in [repo] for [description]."*

---

## Anti-Patterns to Avoid

- ❌ Saving agent outputs as permanent local files in `~/Discovery/` — attach to OP instead
- ❌ Duplicating the same doc in Notion AND GitHub — pick one, link to the other
- ❌ Putting credentials or secrets in any of the above — use `~/.ste-secrets/.env`
- ❌ Using local Obsidian as the primary store for team-shared content
